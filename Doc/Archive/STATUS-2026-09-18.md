## The blind spot was never the loader

ST-5's premise was "the engine's loader runs, its tracer says nothing, so instrument the call sites".
The premise was half right, and the half that was wrong is the useful part.

0.1.9.101 added a second sink — the same low-volume lines go to `portDiagLog` (→ `gpuinit-steps.txt`,
the channel that has survived every crash and hang here) **as well as** to `port-trace.txt` — plus a
lifecycle probe. One run separated every remaining possibility:

| Marker | What it proved |
|---|---|
| `PS: install has=0 didInstall=1 fcc=C:\…\LocalState\…` | `FONTCONFIG_FILE` is visible from `PortPlatformStrategies.cpp`; the environment was never the issue |
| `PS: createLoaderStrategy` | WebCore asks **our** factory for the loader strategy |
| `loader: CALL https://news.ycombinator.com/news.css?…` (×5) | `CachedResource::load` reaches our `loadResource` |
| `loader: serve started=5 inflight=0 pending=0 hosts=0` | the scheduler serves them and drains |

The call sites, the environment and the bridge were all fine. The fault was inside
`portLoaderTrace`'s own file sink: `fopen_s(&file, path, "a")` produced no file while the driver's
`fopen(path, "ab")` on the byte-identical path always did. 0.1.9.102 mirrors the proven function and
adds a one-shot self-report. Measured on 0.1.9.102: `PT: sink ok path=…\LocalState\port-trace.txt`,
and `port-trace.txt` went from **0 to 53** `loader:` lines in one session.

**Honest limit, recorded rather than smoothed over:** the rewrite changed `fopen_s`→`fopen`,
`"a"`→`"ab"` and added `fflush` in one step, so **which one mattered is not isolated**. The sink works
and now reports its own state; the mechanism is unproven.

## The blank page moved, and the loader is out of the picture

For the dzen generation (`g5`):

    loader: CALL https://sso.dzen.ru/install?uuid=…   loader: +…049CE0 g5 → -…049CE0 g5 h=1
    loader: CALL https://sso.dzen.ru/log?uuid=…       loader: +…03F8F0 g5 → -…03F8F0 g5 h=1
    loader: serve started=7 inflight=0 pending=0 hosts=0

Every request starts, every one retires, no `DECLINED`, no `h=0` host miss, nothing left open, nothing
crossed teardown — and that matches the diag's `pending=0` exactly. `install?uuid=…` is `s2`
(**Cached — it loaded**); `log?uuid=…` is `s3` (`LoadError`). **The page is not waiting on anything**,
so this is finally a *measured* exoneration of the scheduler rather than the empty-file accident that
produced the same words earlier today.

One line above that sits the structural finding. The session's **only** top-level fetch is

    SL: curl download url=https://dzen.ru → 302 → sso.passport.yandex.ru/push?uuid=…&retpath=… → 200,
    2883 bytes → SL: DocumentWriter feed → feed done

and the document then *reports* the URL `https://sso.dzen.ru/install?uuid=…` — **a URL that was never
fetched as a top-level document.** The 2883-byte response is a JS redirect page; its navigation made a
new `DocumentLoader`, and `body=0`, `rootKids=-1`, `bodyKids=-1`, `rs=I` is what a document looks like
when its bytes never arrive. `ApoFetchChannel` serves only navigations the *harness* asks for, so a
page-initiated one must be served by the engine's own `FrameLoader` → `DocumentLoader` →
`ResourceHandle` path — the one path no diagnostic covers. That is ST-6 in
[PLAN.md](PLAN.md).

## Tooling: a verdict from an empty trace is now impossible

`Src/tools/analyze-loader-trace.ps1` was refusing nothing. It now stops with exit code 2 and an
explicit "cannot conclude" when neither file has loader traffic — verified against the real `.100`
trace that previously yielded `verdict: the scheduler is exonerated`. It also reads `gpuinit-steps.txt`
in addition to `port-trace.txt`, and a second guard covers the subtler case: `MARK` lines present
while the `+`/`-` pairs (bulk channel, file-only) are not, which would have printed
`starts / finishes : 0 / 0` all over again. The final verdict now requires that pairs exist.

**ST-5 item 2 — merging the two tracers into a shared `PortTrace.h` — deliberately not done.** The
code comment asks for it on the next rebuild of `WebCoreDriver.cpp`; that is not this change, and a
refactor inside a diagnostic build would make a confusing result unattributable.

## Correction to this morning's dzen.ru paragraph (the paragraph below is WRONG)

The paragraph headed "dzen.ru — blank white page" says the port "uses an ephemeral in-memory curl
jar with `CookieAcceptPolicy::OnlyFromMainDocumentDomain`, which may reject the cross-host SSO
cookies". **All three parts of that are wrong, and each was checked in the tree, not inferred:**

1. **Not a curl jar.** The store is WebCore's `CookieJarDB` (sqlite; `:memory:` when the session is
   ephemeral — `NetworkStorageSessionCurl.cpp:93`). curl's own cookie engine is off for engine
   requests (`CurlContext.cpp:328`, `CURLOPT_COOKIEFILE, nullptr`).
2. **The accept policy was never applied.** `ensureDefaultPortStorageSession()` — the only caller of
   `setCookieAcceptPolicy` — **is called from nowhere in the tree**. That line is dead code, and the
   policy actually in force is `CookieJarDB`'s own default, `CookieAcceptPolicy::Always`
   (`CookieJarDB.h:76`), the most permissive value there is. A DEAD CODE note now sits above the
   function.
3. **That jar never saw the top-level document at all.** `ApoFetchChannel::run()`
   (`WebCoreDriver.cpp`) fetches main documents on its own curl handle and feeds the bytes to
   `DocumentWriter`; WebCore believes the loader supplied them. So the jar above is not on the path
   that mattered.

## What was changed and measured

- **ST-2 (cookie engine).** `curl_easy_setopt(h, CURLOPT_COOKIEFILE, "")` on the fetch handle.
  Measured: `SL: fetch ... redirects=1 cookies=9` where every other URL in the session shows
  `cookies=0`. The engine was genuinely missing and now works.
- **ST-3 (redirect chain) — DONE.** A `CURLOPT_HEADERFUNCTION` on the fetch handle records every
  response hop. The chain is now a log line instead of an inference:
  `SL: hop[0] status=302 setcookie=3 loc=...` / `SL: hop[1] status=200 setcookie=6 loc=-`.
- **ST-4 (one jar for both network paths) — DONE, and it did NOT fix dzen.** After the fetch, each
  hop's `Set-Cookie` is filed into WebCore's jar with
  `NetworkStorageSession::setCookiesFromHTTPResponse(firstParty, hopUrl, value)`, on the **engine
  thread** (`defaultPortStorageSession()` asserts `isMainThread()`), with hop URLs reconstructed by
  following `Location`. Measured: `SL: cookies applied=9 hops=2`, applied before the HTML reaches
  `DocumentWriter`, i.e. before the page's own JS navigated. **dzen.ru still renders nothing:**
  `url=https://sso.dzen.ru/install?uuid=...`, `body=0`, `nonwhite=0/710656`, `rs=I`,
  `res:[install?uuid=...(s2) log?uuid=...(s3)]` — byte-for-byte the same diag as before the fix.

**The cookie hypothesis is therefore falsified as an explanation of the blank page.** The jar split
was real and is now closed; it was not the cause. Note that in `res:[...]` the digit is
`CachedResource::Status`: `s0` Unknown, `s1` Pending, **`s2` Cached (the resource loaded)**, **`s3`
LoadError**, `s4` DecodeError. An earlier reading of these as "stage numbers, never loaded" was
wrong and produced a false conclusion about two subresources.

## The blind spot that remains

`port-trace.txt` for both the `.99` and `.100` runs contains **zero `loader:` lines** out of ~1700,
while Hacker News shows five subresources at status `Cached` and `nonwhite=587134/710656`. The
engine's loader demonstrably runs; its tracer says nothing. `PortPlatformStrategies.cpp:60-67`
explains the duplication of the tracer (internal linkage in `WebCoreDriver.cpp`) and asks for the
two to be unified "the next time that file has to be rebuilt anyway" — that moment has arrived.

**Consequence, and it is the important one:** `Src/tools/analyze-loader-trace.ps1` ran against that
empty trace and printed a confident `verdict: the scheduler is exonerated -- every request started
and retired`. Every number it printed was a zero read from an empty input. **A verdict from an empty
trace is worse than no tool**; a guard is owed.

## ⚠️ Do NOT use `x64-cycle.ps1` for a data-preserving update (VERIFIED)

Despite its header, [Src/tools/x64-cycle.ps1](../Src/tools/x64-cycle.ps1) **REMOVES the installed
package** before install: lines 98–101 query the package, call `Remove-AppxPackage` if it exists,
then `Add-AppxPackage`. This wipes LocalState. For an in-place, data-preserving update use the
route recorded for .93: back up LocalState and manifest, bump the version, build Release and
update with `Add-AppxPackage` **without removal**, then verify package identity and retained data.
This documentation refresh does not execute that procedure or alter the script.
